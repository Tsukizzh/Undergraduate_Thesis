## 🔴 代码开发铁律（血泪教训，必须遵守）

以下规则来自本项目的实际经验，违反任何一条都会导致严重的时间浪费：

### 1. 第一版代码就必须包含性能优化
**不是"先写功能再优化"，而是"优化就是功能的一部分"。**

| 必须包含 | 原因 | 真实案例 |
|---------|------|--------|
| 多 worker 并行 | 单线程浪费 90% CPU | build_pt_cache.py 单线程 5h → 10 worker 2min |
| 断点续跑 | 中断后从头跑 = 白费 | 添加 shard 存在检查，中断后自动跳过已完成部分 |
| 向量化操作 | Python for 循环比 torch 慢 100x | bond 过滤 for 循环 → torch.isin 100x 加速 |
| 资源检查 | 文件 >2GB 在 Windows torch 上崩溃 | ESM 分片 2.1GB → torch.load 失败，被迫重新分片 |

### 2. 写完必须多轮审核
- 每个脚本至少和 Codex 做 2 轮审核
- 第一轮：逻辑正确性（字段名、数据类型、特征顺序）
- 第二轮：性能 + 边界情况（大文件、空数据、跨平台）

### 3. 测试先行
- 先用 10 个样本小规模测试
- 确认正确后再跑全量
- 全量完成后做结构完整性验证

## 背景：当前状态与关键澄清

### 当前训练（Step 9）的真实性质

Step 9 AllSplit 训练**不是论文的纯复现**。训练时已经通过 monkey-patch 修复了边排序 bug，因此得到的 AUC=0.7667 是"论文架构 + 边修复"的结果，不是论文原始架构的结果。

这意味着：
- 0.7667 和论文的 0.7198 不能直接对比（不是同一个架构）
- 0.7667 的提升可能来自边修复、也可能来自 6.56% 底物泄露、也可能两者叠加
- 我们缺少一个"论文原始架构（有 bug）"的 all_split 训练结果作为真正基线

### 数据泄露问题

7 个数据集（brenda + 6 家族）合并后存在跨数据集身份泄露：
- 酶序列泄露：27 个（0.15%）— 可忽略
- **底物指纹泄露：585 个（6.56%）— 不可忽略**

泄露意味着部分测试集底物在训练时被见过，AUC 可能虚高。需要在消融实验前处理。

### readahead=False 已在源码中

Codex 检查确认 `data_representer.py` 和 `structure.py` 中的 `lmdb.open()` 已包含 `readahead=False`。不需要额外添加。但我们自己写的缓存 LMDB 打开方式需要单独检查。

## 第二部分：完整执行计划

### 阶段 0：等待期 + 准备工作（Day 1-3）

当前训练在后台跑到 EarlyStopping，同时做准备工作：

**0-A. 写 .pt 预处理脚本 + 新 Dataset 类（1-1.5 天）**

.pt 文件的 schema（修正版，解决了 ESM 重复存储和字段缺失问题）：

```python
# 每个样本的 .pt 文件只存结构数据和索引，不存共享特征
{
    # === 结构数据（每个样本独有，预计算 k-NN） ===
    'protein_atom_feature': tensor,   # 蛋白原子特征 (N_prot, feat_dim)
    'ligand_atom_feature_full': tensor, # 配体原子特征 (N_lig, feat_dim)
    'ligand_pos': tensor,             # 配体原子 3D 坐标
    'protein_pos': tensor,            # 蛋白原子 3D 坐标
    'ligand_bond_index': tensor,      # 化学键连接 (2, N_bond)
    'ligand_bond_type': tensor,       # 化学键类型
    'knn_edge_index': tensor,         # 预计算的 k-NN 边 (2, N_knn)
    'knn_dist': tensor,               # k-NN 边距离
    'ligand_index': tensor,           # 配体原子的底物索引
    'atom_to_residue': tensor,        # 原子→残基实例编号映射
    'residue_to_seq_pos': tensor,     # 残基实例→ESM序列位置映射
    'str_tag': str,                   # 结构标签

    # === 索引（运行时查找共享特征用） ===
    'enzyme_idx': int,                # 酶编号 → 查 ESM embedding
    'substrate_idx': int,             # 底物编号 → 查 Morgan/GROVER
    'dataset_id': int,                # 数据集编号
    'label': int,                     # 标签（考虑后续可能移到外部 CSV）
}
```

共享特征单独存储（不重复）：

```python
# 酶嵌入：25K 个文件或保留在小 LMDB 中
enzymes/enzyme_{idx}.pt  → {'embedding': tensor (seq_len, 1280)}

# 底物特征：40K 个文件或保留在小 LMDB 中
substrates/substrate_{idx}.pt → {
    'morgan_fp': tensor (1024,),
    'grover_mean': tensor (4885,),
    'grover_atom': tensor (max_atoms, 2400),
    'reaction_graph': Data object,
}
```

分目录存储：

```
processed/
├── samples/
│   ├── 000/  (sample_0.pt ~ sample_999.pt)
│   ├── 001/  (sample_1000.pt ~ sample_1999.pt)
│   └── 176/
├── enzymes/  (enzyme_0.pt ~ enzyme_24999.pt)
└── substrates/  (substrate_0.pt ~ substrate_39634.pt)
```

注意事项：
- 预计算 k-NN 时使用 `edge-mode fixed`（修复后的边排序）
- 保存 k-NN 的原始结果（edge_index + distances），最终的边特征在运行时组装
  这样保留了调整 `dist_noise`（训练/验证不同）和未来改 edge 逻辑的灵活性
- atom_to_residue 和 residue_to_seq_pos 是酶侧融合所需的映射，提前计算好

**0-B. 准备架构修复代码（0.5-1 天）**

三个修复提前写好，但不跑（注意：不是四个，边修复已在 baseline 中）：

1. **Dropout 0.9→0.1**：定位 `ss.py` 中 cross_attention 的 dropout 参数，改数值
2. **Fe 词汇表 + Heme 数据**：
   - 代码改：`transforms.py:23` 蛋白原子词汇表加 Fe(26)
   - 数据改：需要重新跑结构提取，保留 Heme（之前 Gate A 选的 noHeme 配置）
   - **两者必须同时做，否则 Fe 修复是空操作**（当前数据里没有 Fe 原子）
3. **酶侧特征融合**：
   - 需要 `原子 → 残基实例编号 → ESM 序列位置` 的完整映射
   - 设计聚合模块（scatter_mean 按残基聚合）+ MLP 降维
   - **不能按氨基酸类型聚合**（会把不同位置的同类氨基酸混在一起）

**0-C. 处理数据泄露（0.5 天）**

两个选择：
- **方案 A（推荐）**：不改数据，但在评估时计算两个 AUC——"全部样本"和"排除泄露样本"
- **方案 B（更严谨）**：全局去重后重新划分 train/val/test，重新训练所有模型

方案 A 省时间，方案 B 更严谨。考虑到时间紧迫，建议用方案 A，在论文中标注泄露率和干净 AUC。

**0-D. 收集 P450 扩充数据（碎片时间）**

纯数据收集工作，不占计算资源，穿插在其他事情之间做。

### 阶段 0→1 过渡：训练结束，切换管线（半天 - 1 天）

EarlyStopping 触发后：

1. 保存最终 checkpoint → 这是"**边修复后基线**"（不是论文原始基线）
2. 对全量样本执行 .pt 预处理（半天 - 1 天，取决于是否需要重算 k-NN）
3. sanity check：新管线跑 1 epoch，确认 loss 与旧管线一致
4. 速度验证：跑 100 batch 计时
5. 确定后续实验环境

### 阶段 1：消融实验（5-7 天）

**关键原则**：
- **所有实验从头训练**（随机初始化），不能 resume
- **先独立筛选**，再组合有效修复
- Fe 修复需要同时重新生成含 Heme 的结构数据

#### 第一轮：补一个"论文原始架构"基线（1 天）

用不修复边排序的代码（`edge-mode legacy`）从头训练。得到论文原始架构在 all_split 上的真实 AUC。

这一轮的价值：量化边修复本身带来了多少提升。

#### 第二轮：独立筛选每个修复（3-4 天）

每个修复单独测试，都基于"边修复后基线"从头训练：

| 实验 | 改了什么 | 从头训练 | 目的 |
|------|--------|---------|------|
| 2a | 只改 Dropout 0.9→0.1 | 是 | 测 Dropout 单独效果 |
| 2b | 只加 Fe + 重新生成含 Heme 结构 | 是 | 测 Fe+Heme 单独效果 |
| 2c | 只做酶侧融合 | 是 | 测融合单独效果 |

#### 第三轮：组合有效修复（1-2 天）

只组合第二轮中 AUC 有提升的修复。如果三个都有效，组合在一起跑一轮。如果只有一两个有效，只组合有效的。

#### 最终消融表

```
实验 0: 论文原始架构（有边 bug）     AUC = ?    ← 第一轮补跑
实验 1: 修复边排序（Step 9 结果）    AUC = 0.7667（已有，需跑到 EarlyStopping 确认）
实验 2a: 实验1 + Dropout 0.1        AUC = ?    ← 独立测试
实验 2b: 实验1 + Fe+Heme            AUC = ?    ← 独立测试
实验 2c: 实验1 + 酶侧融合            AUC = ?    ← 独立测试
实验 3: 实验1 + 所有有效修复组合      AUC = ?    ← 组合有效的
实验 4: 实验3 + P450 数据扩充         AUC = ?    ← 最终模型
```

每行对比上一行，能清楚看到每个改动的贡献。

注意：实验 0 和实验 1 的差值 = 边修复的贡献。这个数据对论文很有价值。

### 阶段 1.5：数据扩充管线（与阶段 1 并行）

GPU 跑消融实验时，CPU 空闲推进数据扩充：

| 步骤 | 工具 | 耗时 | 占 GPU？ |

### 阶段 2：架构修复 + 扩充数据联合验证（2-3 天）

## 第四部分：核心原则

### 为什么按这个顺序

1. **先确定基线**：补跑"论文原始架构"对照，量化边修复贡献
2. **先独立测，再组合**：避免无效修复被有效修复掩盖
3. **都从头训练**：resume 不是公平对比，论文审稿人会质疑
4. **数据扩充和消融并行**：CPU 跑数据管线不占 GPU
5. **最后多 seed 验证**：单 seed 结果有随机性，不够可靠

### 与中期答辩 PPT 的对应关系

| PPT 内容 | 本计划对应 |
|---------|---------|
| Path C 架构优化：边排序修复 | 已在 Step 9 中完成，需补跑对照 |
| Path C 架构优化：Fe 词汇 | 阶段 1 实验 2b（需同时重新生成含 Heme 结构） |
| Path C 架构优化：Dropout | 阶段 1 实验 2a |
| Path C 架构优化：酶侧融合 | 阶段 1 实验 2c（注意残基映射问题） |
| Path C 数据扩充 | 阶段 1.5（与消融并行） |
| Path C 联合验证 | 阶段 2 |

### 后续扩充数据走同一套流程

.pt 预处理脚本写好后，现有 176K 样本和新扩充数据走同一条管线，写一次用无数次。
