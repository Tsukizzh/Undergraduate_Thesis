## 一、研究全景：我们在做什么

### 1.1 核心研究问题

EZSpecificity（Nature 2025）声称是通用的酶-底物特异性预测模型。我们的研究问题是：**它对 P450 家族的泛化能力如何？如果失败，能否改进？**

### 1.2 三条路径

| 路径 | 目标 | 状态 |
|------|------|------|
| **Path A** | 构建 P450 独立测试集，评估模型表现 | ✅ 完成（AUC=0.6636） |
| **Path B** | 系统诊断 P450 泛化失败的原因 | ✅ 完成（四大发现） |
| **Path C** | 架构优化 + 数据扩充 + 重新训练 | 🔄 进行中 |

### 1.3 Path C 的四个阶段

| 阶段 | 目标 | 数据来源 | 用什么管线 | 需要新 .pt？ |
|------|------|---------|----------|:--:|
| 1. 基线训练 | 训出可对比的 baseline | ESIBank all_split | .pt per-sample 训练 | 当前够用 |
| 2. 架构消融 | 量化每个修复的贡献 | 同上（不改数据） | .pt per-sample 训练 | 不需要（除了 Fe+Heme） |
| 3. Benchmark | 对比原模型 vs 优化模型在 P450 上的表现 | P450 测试集 682 条 | **推理管线**（main_testing.py，Path A 已有） | 不需要 |
| 4. 数据扩充 | 加 P450 专属数据重训 | ESIBank + P450 新数据 | .pt 管线增量扩展 | 需要（只跑新数据） |

**为什么阶段 3 不需要 .pt？**
阶段 3 是推理（inference），不是训练。用 Path A 已经生成好的特征（ESM、GROVER、结构 LMDB），走 `main_testing.py`，不走 .pt 训练管线。

**为什么阶段 4 不需要重跑旧数据？**
build_pt_cache.py 支持增量生成（resume/skip existing）。只需要生成新 P450 数据的 .pt 文件，旧的 176K 样本不动。

### 2.2 Step 10: .pt 训练管线 ✅

**做了什么**：把 60GB LMDB 数据转成 per-sample .pt 文件，消除 mmap 抖动和 CPU k-NN 瓶颈。

**为什么需要这个**：
- 论文作者：256GB+ RAM 服务器，60GB LMDB 全进 page cache = 快
- 我们：32GB/16GB RAM < 60GB LMDB → mmap 换页抖动 → 速度从 3.8 衰减到 2.09 it/s
- .pt per-sample：每次只读 160KB → 无抖动 → 7.56 it/s 稳定

**迭代历史（三次失败两次成功）**：

| 版本 | 做法 | 速度 | 内存 | 问题 |
|------|------|------|------|------|
| v1 分片 | 87 个 300MB 分片 | 0.01 it/s | 9.7GB | SSD 100% 饱和，系统卡死 |
| v2 flatbin | enzyme/substrate 改 seek，graph 仍分片 | 0.38 it/s | 4GB→增长 | graph 分片仍触发 300MB torch.load |
| v2 + 1w | 同上 + 1 worker | 0.52 it/s | ~8GB | 仍然太慢 |
| v2 + 4w | 同上 + 4 worker | 崩溃 | >32GB | EntityTensorCache 4096×7MB=28GB/进程 |
| **v3 per-sample** | **每样本一个 160KB .pt** | **7.33-7.70 it/s** | **~10GB** | **✅ 成功** |

**最终存储布局**：
```
ezspec_pt_v1/ (~57GB)
├── manifest.pt                         (1KB，全局配置)
├── enzymes/
│   ├── enzymes.bin                     (27GB，所有酶的 ESM fp16，用 file.seek 读取)
│   ├── enzymes_index.pt                (酶 ID → bin 文件偏移量)
│   └── enzymes_flatbin_index.pt        (同上，兼容格式)
├── substrates/
│   ├── substrates_grover.bin           (4.3GB，所有底物的 GROVER fp16)
│   ├── substrates_meta.pt              (~430MB，grover_mean + morgan)
│   └── substrates_index.pt             (底物 ID → bin 文件偏移量)
├── train/
│   ├── index.pt                        (样本元信息：sample_id, enzyme_id, substrate_id, label...)
│   └── samples/                        (176,843 个 .pt 文件，分 177 个子目录)
│       ├── 000/ (sample_000000.pt ~ sample_000999.pt)
│       ├── 001/ (sample_001000.pt ~ sample_001999.pt)
│       └── 176/ (sample_176000.pt ~ sample_176842.pt)
├── val/
│   ├── index.pt
│   └── samples/                        (1,482 个 .pt 文件)
└── test/
    ├── index.pt
    └── samples/                        (8,841 个 .pt 文件)
```

**每个 per-sample .pt 文件包含什么**（~160KB）：
```python
{
    # 结构数据
    'ligand_pos': tensor,           # 配体原子 3D 坐标
    'ligand_element': tensor,       # 配体原子元素类型
    'ligand_atom_aux': tensor,      # 配体化学属性（芳香性、度、氢数、杂化）
    'ligand_index_raw': tensor,     # 配体原子的底物索引
    'protein_pos': tensor,          # 蛋白原子 3D 坐标
    'protein_element': tensor,      # 蛋白原子元素类型
    'protein_aa_type': tensor,      # 氨基酸类型
    'protein_is_backbone': tensor,  # 是否骨架原子
    'bond_index': tensor,           # 化学键连接关系
    'bond_type': tensor,            # 化学键类型（单键/双键/三键/芳香键）
    'knn_edge_index': tensor,       # 预计算的 k-NN 边（k=48，最耗时的部分）
    # 元数据索引
    'enzyme_id': int,               # → 去 enzymes.bin 查 ESM 嵌入
    'substrate_id': int,            # → 去 substrates_grover.bin 查 GROVER
    'dataset_id': int,              # 来自哪个数据集
    'str_tag_code': int,            # complex=0, ligand=1
    'label': int,                   # 正/负样本
    'sample_weight': float,         # 样本权重
}
```

**训练时的数据加载流程**（每个样本 <1ms）：
1. torch.load 一个 160KB 的 .pt 文件 → 拿到结构数据 + enzyme_id + substrate_id
2. file.seek 读 enzymes.bin 的对应位置 → 拿到 2MB 的 ESM 嵌入 → fp16→fp32 + padding 到 [1450, 1280]
3. file.seek 读 substrates_grover.bin → 拿到 GROVER + Morgan
4. 从原子类型重建 one-hot 特征（torch 向量化，几微秒）
5. 从坐标 + 预算的 knn_edge_index 重算距离 + Gaussian 展开（几微秒）
6. 按 edge_mode（fixed/legacy_bug）组装边索引和边特征
7. 组装成 PyG Data 对象 → 送 DataLoader → 送 GPU

**关键文件**：
| 文件 | 位置 | 作用 |
|------|------|------|
| pt_dataset.py | scripts/10_Step10_pt训练管线/ | Dataset 类，读 .pt 文件 |
| main_training_pt.py | scripts/10_Step10_pt训练管线/ | 训练脚本（PyTorch Lightning） |
| build_pt_cache.py | scripts/09_Step9_AllSplit训练/ | .pt 文件生成脚本（本地用） |
| server_config.yml | scripts/ | 服务器训练配置 |

**1 epoch 完整训练结果**（本地，num_workers=2）：
| 指标 | 值 |
|------|------|
| 时间 | 29 分钟 |
| 速度 | 7.33 it/s（稳定，不衰减） |
| val AUC | 0.6103（随机初始化第 1 个 epoch，正常） |
| 内存 | ~10GB |

### Step 13：独立消融实验

#### 目的
逐个测试每个架构修复的效果，找出哪些修复有用。

#### 关键原则
1. **所有实验从头训练**（随机初始化）——不能从 Step 11 的 checkpoint resume
2. **先独立测每个修复**——不要一次改多个变量
3. **和 Step 11 第二轮（fixed 基线）对比**——每个修复和同一个基线比

#### 13a：Dropout 0.9→0.1

**改什么**：`train_allsplit_config.yml` 中 `cross_attention.dropout: 0.9` 改为 `0.1`

**为什么**：论文的 Dropout=0.9 极其激进（丢弃 90% 的注意力连接）。对于 P450 这种训练数据稀缺的家族，太高的 Dropout 让酶-底物交互信号很难被学到。

**操作**：
1. 复制 server_config.yml 为 config_dropout01.yml
2. 改 `cross_attention.dropout: 0.1`
3. 传到服务器
4. 跑训练（同 Step 11 命令，改 --config）

**预期**：AUC 可能提升 0.01-0.03（Dropout 太高确实损害学习）

**耗时**：1-2 天

#### 13b：Fe 词汇 + Heme 数据

**改什么**：
1. **代码**：`transforms.py:23` 蛋白原子词汇表加 Fe(26)
2. **数据**：重新生成含 Heme 的结构 → 重新生成 .pt 文件

**为什么**：
- P450 的催化核心是 Heme 辅因子，中心是 Fe 原子
- 当前词汇表只有 [H, C, N, O, S, Se]，不含 Fe
- Fe 被编码为全零向量，通过 GNN 消息传递扩散噪声
- 2×2 因子实验证据：加 Heme 后 AUC 从 0.7115 暴跌到 0.4894（主效应 -0.2322）
- 修复 Fe 词汇后，Heme 不应再崩溃

**操作**：
1. 本地修改 transforms.py 加 Fe
2. 本地重新生成含 Heme 的结构特征（pocket 提取时保留 Heme）
3. 本地重新跑 build_pt_cache.py 生成新的 .pt 文件
4. 传到服务器
5. 跑训练

**这步最复杂**：不是改一行代码就行，需要重新走结构处理管线。

**预期**：如果 Fe 修复有效，Heme 信息应该帮助模型理解 P450 活性位点，AUC 可能显著提升。

**耗时**：2-3 天（含数据准备）

#### 13c：酶侧结构融合

**改什么**：
- 当前模型只用底物侧的结构特征，酶口袋原子特征被丢弃
- 修复：将口袋原子特征按残基聚合，和 ESM 嵌入拼接

**为什么**：
- EGNN 处理完 3D 复合物后，每个原子都有 128 维特征
- 但模型只用了底物原子特征，酶口袋特征被丢弃
- 酶侧只有序列信息（ESM），没有结构信息
- 融合后酶侧同时拥有序列 + 结构信息

**技术难点**：
- ESM 是残基级（1 个氨基酸 = 1 个向量）
- EGNN 是原子级（1 个原子 = 1 个向量）
- 需要 atom→residue_instance→ESM_position 的完整映射
- **不能按氨基酸类型聚合**（会混淆不同位置的同类氨基酸）
- 代码里的 `atom_to_aa_type` 是类型，不是实例编号

**操作**：
1. 修改结构处理代码，保存 atom→residue 映射
2. 修改 ss.py 的 forward，加融合模块
3. 重新生成 .pt 文件（包含映射信息）
4. 训练

**预期**：效果不确定。融合理论上应该有帮助，但实现复杂度高，容易出 bug。

### Step 15：P450 数据扩充（可和 Step 13 并行）

#### 目的
从外部数据库收集 P450 酶-底物数据，扩充训练集。

#### 数据来源

| 来源 | 预计规模 | 特点 |
|------|---------|------|

| PCPD (p450.biodesign.ac.cn) | 181 条 | 有结构，质量高 |

#### 数据处理流程（全在本地做）

```
1. 收集序列 + 底物 SMILES
   ↓
2. AlphaFold 预测酶 3D 结构
   ↓
3. AlphaFill 填充 Heme 辅因子
   ↓
4. AutoDock Vina 对接（复用 Path B 管线）
   ↓
5. ESM-2 序列嵌入 → append 到 enzymes.bin
6. GROVER/Morgan 分子指纹 → append 到 substrates_grover.bin
7. 结构特征提取 → build_pt_cache.py 生成新 per-sample .pt
   ↓
8. 合并到 ezspec_pt_v1/，更新 index.pt
   ↓
9. 传到服务器训练
```

#### CPU/GPU 并行
- 步骤 1-4, 7：纯 CPU 工作，不占 GPU
- 步骤 5：需要 GPU（ESM-2 推理），等消融实验间隙跑
- 步骤 6：纯 CPU
- 可以和 Step 13 完全并行：GPU 跑消融，CPU 跑数据处理

#### 负样本策略改进
基于 Path B 的发现，新数据的负样本做两个改进：
1. **硬负样本**：负酶与正酶来自同 EC 前 3 位（难度≥3），而非混合难度 0-5
2. **双向采样**：同时包含方向 A（固定底物换酶）和方向 B（固定酶换底物）

## 五、决策树（遇到问题怎么办）

### 服务器相关
```
速度太慢（<2 it/s）？
├─ 检查 per-sample 文件是否存在
├─ 检查 num_workers（16GB RAM 用 1-2）
├─ 检查是否走了 fallback 分片模式（日志有提示）
└─ 备选：租云服务器 RTX 3090 100GB RAM ¥0.99/h

CUDA out of memory？
├─ --batch-size 8（减半）
├─ --num-workers 0
└─ 检查是否有其他进程占 GPU

nohup 训练中断？
└─ --resume last 恢复（checkpoint 自动保存）
```

### 实验相关
```
消融实验都没提升？
├─ 确认 sanity check 通过（新管线 loss 和旧管线一致）
├─ 确认跑够 epoch（至少 15 个 epoch 才能判断）
├─ 如果架构改动无效 → 问题在数据 → 优先 Step 15 数据扩充
└─ 最坏情况：报告"修复无效"也是有价值的负结果

Fe+Heme 结构重新生成来不及？
├─ 先跑 13a（Dropout）和 13c（融合）
└─ Fe+Heme 放到有时间再做

时间不够跑完所有实验？
├─ 最低要求：实验 0 + 实验 1 + 最有希望的 1 个修复
├─ 这 3 个实验 + Path A/B 的结果，足以撑起论文
└─ 数据扩充也可以简化（只用最容易获取的 Plant P450 DB）
```

## 六、代码开发铁律（15 条血泪教训）

### 存储格式
1. **PyG 标准 = per-sample .pt 文件**，不要自定义分片格式
2. **torch.load 只适合 <10MB 文件**，大文件用 file.seek + np.frombuffer
3. **共享数据不重复存**，用索引引用（enzyme/substrate 存一份，样本存索引号）

### 内存管理
4. **缓存大小必须计算**：entries × per-entry-MB ≤ 可用 MB
5. **Windows spawn 模式**：num_workers × 单进程内存 ≤ 总 RAM
6. **__getstate__ 和 __init__ 必须同步**

### 磁盘 I/O
7. **大文件随机 torch.load = SSD 饱和**（300MB × 多次 = 15TB/epoch）
8. **小文件顺序读 = SSD 空闲**（160KB × 176K = 28GB/epoch）

### 测试方法
9. **用真实训练测速**（forward + backward + optimizer），不要只测数据加载
10. **小数据集（val 1482）不代表大数据集（train 176K）**
11. **监控 SSD 利用率和内存趋势**，不只看 it/s

### 数据生成
12. **多 worker 并行**：单线程 5 小时 → 10 worker 2 分钟（150 倍加速）
13. **向量化替代 Python 循环**：for-loop → torch.isin = 100 倍加速
14. **断点续传是必需品**：长脚本必须跳过已有文件

### 开发流程
15. **第一版就加优化**——不是"先写功能再优化"，优化是功能的一部分
