## 一、训练数据流水线详解

### 1.1 完整数据流：从硬盘到GPU

当我们开始训练时，数据会按照以下流程流动：

```
┌─────────────────────────────────────────────────────────────────┐
│  物理硬盘                                                         │
│  └─ 60GB LMDB 数据库                                            │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 读取（通过 mmap 内存映射）
┌──────────────────────────▼──────────────────────────────────────┐
│  系统内存 (RAM)                                                   │
│  └─ 页缓存 (Page Cache)                                          │
│     └─ LMDB 数据页面 (通常最近访问的数据)                         │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 反序列化 pickle → Python 对象
┌──────────────────────────▼──────────────────────────────────────┐
│  CPU 工作线程 (DataLoader workers)                               │
│  ├─ 读取 LMDB 和 pickle                                         │
│  ├─ k-NN 图计算 (scipy 库)  ← 最费时的部分 (50-70%)             │
│  ├─ 特征填充和标准化                                              │
│  └─ 转换为 PyTorch 张量 (Tensor)                                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 数据队列 (DataLoader buffer)
┌──────────────────────────▼──────────────────────────────────────┐
│  主进程 (Main Process)                                           │
│  └─ 批处理 (Batch)：32 个样本合并成一个批                         │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 转移到 GPU
┌──────────────────────────▼──────────────────────────────────────┐
│  GPU 显存 (VRAM)                                                 │
│  └─ 11.4 GB 数据                                                 │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 神经网络计算
┌──────────────────────────▼──────────────────────────────────────┐
│  GPU 计算核心                                                     │
│  ├─ GNN 消息传递 (~10ms)                                         │
│  ├─ 交叉注意力 (~5ms)                                            │
│  └─ 损失计算 (~2ms) = 总计 ~17ms                                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │ 返回梯度
┌──────────────────────────▼──────────────────────────────────────┐
│  优化器 (Optimizer)                                               │
│  └─ 更新模型权重                                                 │
└──────────────────────────▬──────────────────────────────────────┘
```

**关键时间成本**：
- **GPU 计算**: ~17 毫秒/批 ✓ 很快（小模型）
- **CPU 数据准备**: ~2000-3000 毫秒/批 ✗ 超级慢！
- **结果**: GPU 计算 17ms，等待数据 2000ms → **GPU 利用率仅 0.8%!**

### 1.2 数据文件与其大小

在我们的项目中，有多个 LMDB 数据库需要被加载：

| 文件 | 大小 | 用途 | 数据类型 |
|------|------|------|---------|
| enzyme_features.lmdb | 50GB → 35GB (fp16) | 酶蛋白序列的 ESM-2 嵌入向量 | 1280→128 维 |
| reaction_features.lmdb | 25GB | 底物分子的图特征 | 原子图结构 |
| structure_features.lmdb | 250MB | 对接复合物的口袋和配体坐标 | 3D 坐标 |
| 其他特征 (Morgan, GROVER) | 3GB | 分子指纹 | 向量 |
| **总计** | **60GB** | 所有特征的并集 | 混合 |

当我们训练时，这些文件被**内存映射 (mmap)**：系统不是立即加载全部 60GB，而是"声称"拥有这 60GB，实际上只在需要时才从硬盘读取。

### 1.3 k-NN 计算是什么，为什么它很慢？

**问题**: 对于每个分子样本，我们需要找到它的 **k=32 个最近邻居原子**，用来构建图的边。

**实现**: 使用 scipy 库的 KDTree 在 CPU 上计算
```python
# 伪代码
for sample in batch:
    coords = sample.coordinates  # ~50 个原子的坐标
    tree = scipy.spatial.KDTree(coords)  # 构建树结构 ~5ms
    edges = tree.query(coords, k=32)     # 查询邻居 ~10ms
    # 总计 ~15ms per sample × 32 samples = ~480ms per batch!
```

**为什么这是瓶颈？**
- scipy 在 CPU 上运行，不能并行化
- 每个批处理的 32 个样本都要重复这个计算
- CPU 的单核频率有限，不是 GPU 那样的大规模并行

### 1.4 为什么 GPU 使用率这么低？

我们的模型只有 **180 万参数** (1.8M params)，相比之下：
- ResNet-50: 2500 万参数
- BERT: 1.1 亿参数
- GPT-3: 1750 亿参数

这意味着：
- **模型计算**: 17 毫秒（超快！）
- **数据加载**: 2000+ 毫秒（超慢！）
- **GPU 等待数据的时间**: 99% 时间在闲等

这不是用户的错——这是图神经网络社区的**通常问题**。GNN 本身计算量小，但需要复杂的数据预处理。

## 二、三个核心痛点

### 痛点 1: LMDB mmap 内存抖动

#### 什么是 mmap？

**内存映射文件 (mmap)** 是操作系统的一种机制：
- 不把 60GB 文件全部读入 RAM（不可能，我们只有 32GB）
- 而是"虚拟地"映射到地址空间，需要时才读取

#### 什么是页抖动（Page Thrashing）？

当 RAM 满了，系统会：
1. 使用磁盘空间作为"虚拟内存" (swap)
2. 快速地在 RAM 和硬盘间**交换数据页面**

在我们的情况下：
- 60GB LMDB 数据库，but 只有 32GB RAM
- 为了取得某个原子的坐标，系统可能要：
  - 从硬盘读取该数据页 (~5ms)
  - 把其他不用的页丢到硬盘 (~5ms)
  - 再重新读取之前的页 (~5ms)
  - **每次访问变成 15ms 而不是 1ms**

**实际观察**：
```
系统内存使用: 32GB (99% 满载)
虚拟内存 (Swap) 活动: 5.8GB
→ 训练速度从 4.3 it/s 降到 2.09 it/s（50% 性能损失）
```

### 痛点 2: CPU k-NN 计算瓶颈

**数据加载时间分解** (per batch):

| 操作 | 时间 | 占比 |
|-----|------|------|
| 从 LMDB 读取 pickle | 5-8ms | 15-25% |
| **k-NN 图计算 (scipy)** | **10-50ms** | **50-70%** ⚠️ |
| 特征填充和张量化 | 1-2ms | 5-10% |
| 原子特征编码 | <1ms | ~2% |
| **总计** | **20-60ms** | **100%** |

**问题**：
- CPU 在计算 k-NN 时，GPU 就在空闲
- 32 个 CPU worker 仍然无法加快这个过程（单个 scipy 计算无法并行化）

### 痛点 3: GPU 空闲

**我们的 GPU 使用率分析**：

```
时间线 (单位: 毫秒)
├─ 0-2000ms: GPU 计算前向/反向传播 (实际计算: 17ms)
├─ 2000-4000ms: GPU 在等待 CPU 加载下一批数据
├─ 4000-6000ms: GPU 再次计算 (17ms)
├─ 6000-8000ms: GPU 再次等待
└─ ...（重复）

结果: GPU 计算时间 / 总时间 = 17 / 4000 = 0.4% 有效利用
     (实际测得: 0.8% 平均，最高 94% 瞬间)
```

这被称为**"脉冲模式"** — GPU 间歇性地工作，而不是持续工作。

## 三、已经尝试过的方案

### 3.1 方案 2: 240GB 结构缓存（Method 2）

**想法**：预先计算所有样本的 k-NN 图，存入缓存，训练时直接读取（不再需要 scipy 计算）

**结果**：

| 指标 | 无缓存 | 缓存 | 对比 |
|-----|--------|------|------|
| k-NN 计算时间 | 每批 500ms | 0ms | ✅ 消除 |
| 缓存大小 | 0GB | 240GB | ⚠️ 加重 |
| 总 mmap 尺寸 | 60GB | 300GB | ⚠️ 加重 |
| 早期速度 (ep0-3) | 4.5 it/s | 4.5 it/s | ❌ 无收益 |
| **后期速度 (ep14-19)** | **4.3 it/s** | **2.09 it/s** | ❌ 反而变慢! |
| 基准测试 (300批) | — | 14.93 it/s | 仅适用于页缓存场景 |

**为什么变慢了？**
- 缓存本身就占 240GB
- 加上其他 LMDB 数据库共 300GB
- 32GB RAM 无法容纳全部，mmap 页面交换更加频繁
- 反而使问题**恶化**

**结论**：缓存只在数据能完全放入 RAM 时才有用（需要 ≥256GB RAM）

### 3.2 方案 E: fp16 酶 LMDB（已完成）

**想法**：把酶特征从 float32（32 位）压缩为 float16（16 位），减少 LMDB 大小

**结果**：
- 酶 LMDB: 50GB → 35GB （减少 30%）
- **总 mmap**: 60GB → 45GB （减少 25%）
- **速度改进**: 仅 +5-10%，仍然无法突破 32GB 页缓存限制

**结论**：这是一个小改进，但不够根本解决问题

### 3.3 无缓存模式（server_train.py）

**想法**：不预计算 k-NN，每次都现算，减少 mmap 压力

**结果**：
- mmap 大小: 300GB → 60GB （大幅减少！）
- k-NN CPU 瓶颈: 回来了（50-70% 数据加载时间）
- **速度**: 1.35-4.3 it/s （取决于其他参数）

**结论**：解决了 mmap 问题，但引回了 CPU 瓶颈

## 四、所有可行方案（完整版）

### 方案 F★: LMDB 读取参数优化（零成本，最先尝试）

#### 问题
操作系统有一个"预读（readahead）"机制：当你读取文件第 1 个字节时，系统会自动把接下来的几 MB 也读进来，因为大多数程序都是顺序读取文件。

但在我们的情况下：
- LMDB 数据库被**随机访问**（DataLoader 随机打乱样本顺序）
- 预读机制浪费了大量 RAM，反而减速

#### 方案
在打开 LMDB 数据库时加入三个参数：
```python
db = lmdb.open(
    path,
    readahead=False,   # 关闭文件系统预读
    meminit=False,     # 跳过初始化检查
    lock=False         # 无需多进程锁（只有训练进程读）
)
```

#### 依据
- **LMDB 官方文档** 明确说："当随机访问超过 RAM 的大文件时，应禁用预读"
- **PyTorch 社区实现** (xformers, detectron2, timm) 都使用这个配置
- **多个研究项目** 报告 +5-15% 加速

#### 预期效果
当前速度: 2.09 it/s → **目标: 2.2-2.4 it/s** (+5-15%)

#### 实施
非常简单，找到加载 LMDB 的代码，通常在 `cache_utils.py` 或 `brenda.py` 中：
```python
# 搜索: lmdb.open
# 修改这一行:
db = lmdb.open(path, readonly=True)

# 变成:
db = lmdb.open(path, readonly=True, readahead=False, meminit=False, lock=False)
```

#### 风险
**零风险** — 这是纯读优化，不涉及写入或多进程同步

#### 试验步骤
1. 应用上述修改
2. 恢复训练: `--resume last` （从 ep19 继续）
3. 监测 ep20 的速度，与 ep19 基线 (2.09 it/s) 对比
4. 如果有改进，记录下来并继续

#### 原理

- 消除 LMDB mmap（完全）

#### 实施难度
- **磁盘**: 250-300GB （加重磁盘 4-5 倍）

#### 预期效果
- **速度**: 理论上 +100-150% （从 2.09 → 4-5 it/s）

### 方案 D: GPU k-NN 流水线（架构改进）

#### 想法（更新于 2026-03-15）
在 GPU 上计算 k-NN，而不是 CPU 的 scipy

#### 之前的误解
原本认为"GPU k-NN 需要 num_workers=0"（串行数据加载），这会**丢失并行化好处**。

#### 正确的做法（PyG 官方文档）
```python
# 工作流程:
# 1. DataLoader workers (CPU, 并行) 读取 LMDB + 特征
# 2. 主进程拿到数据后，在 GPU 上计算 k-NN
# 3. 返回完整的图结构
# 4. GPU 进行 GNN 计算

# 代码示例：
def collate_fn(batch):
    # 这个函数在主进程运行，可以访问 GPU
    coords_list = [sample['coords'] for sample in batch]

    # 【关键】构建 batch 向量，标记每个原子属于哪个分子
    # 没有这个参数，k-NN 会跨分子连边（严重 bug！）
    # 例如：分子A有50个原子，分子B有80个原子
    # batch_vec = [0,0,...,0, 1,1,...,1]  (50个0 + 80个1)
    batch_vec = torch.cat([
        torch.full((len(coords),), i, dtype=torch.long)
        for i, coords in enumerate(coords_list)
    ])

    # 拼接所有原子坐标
    coords_all = torch.cat([
        torch.from_numpy(c).float() if not isinstance(c, torch.Tensor) else c
        for c in coords_list
    ])

    # 在 GPU 上计算 k-NN，batch 参数确保只在同一分子内部连边
    edges = torch_cluster.knn_graph(
        coords_all.cuda(),
        k=32,
        batch=batch_vec.cuda(),  # ← 必须传入！否则跨分子连边
        flow='target_to_source'
    )

    return {
        'edges': edges.cpu(),
        'batch': batch_vec,
        # ... 其他特征
    }
```

> **⚠️ 重要警告**：`knn_graph` 处理多个分子的 batch 时，**必须传入 `batch` 参数**。
> 否则所有原子会被当成同一个分子，导致跨分子连边——这是训练结果错误的 bug，不是性能问题。
> 如果只处理单个分子（不是 batch），则不需要 batch 参数。

#### 优势
- **消除 CPU k-NN 瓶颈** （减少 50-70% 数据加载时间）
- **保留多 worker 并行** （仍然用 6 个 worker 读取 LMDB）
- **GPU 计算能力强** （k-NN 在 GPU 上比 scipy 快 10-100 倍）

#### 实施难度
- **磁盘**: 无变化（仍是 60GB LMDB）
- **代码**: 中等难度（修改 EdgeConnection 类和 collate_fn）
- **时间**: 1-2 天

#### 预期效果
- **速度**: +50-80% （从 2.09 → 3.2-3.8 it/s）
- **GPU 利用率**: +20-30%

#### 需要的库
```bash
pip install torch_cluster  # PyG 官方 k-NN 库
# 或使用 pytorch3d
pip install pytorch3d
```

#### 代码改动示例
```python
# 原始 EdgeConnection (CPU scipy)
def get_edge_index(coords):
    tree = scipy.spatial.KDTree(coords)
    _, neighbors = tree.query(coords, k=32)
    return neighbors_to_edges(neighbors)

# 改进版 (GPU)
def get_edge_index_gpu(coords):
    coords_gpu = coords.cuda()
    edge_index = torch_cluster.knn_graph(coords_gpu, k=32)
    return edge_index.cpu()
```

### 方案 H: 给导师服务器升级 RAM

```

存储: 充足
```

#### 问题
- 16GB < 60GB LMDB，页缓存压力更大
- 单通道 RAM 带宽限制（本地值：双通道带宽的 50%）

#### 升级方案
```
升级前:                升级后:
16GB (单通道)    →     32GB (双通道)

优势:
1. 页缓存容量翻倍 → mmap 抖动减轻（但 32GB < 60GB LMDB，不能完全消除）
2. 双通道 → RAM 带宽翻倍
3. 配合 readahead=False 效果更好

局限:
- 32GB 仍不足以容纳全部 60GB LMDB 数据
- 要彻底消除 mmap 抖动需要 ≥ 80GB RAM

如果升级到 64GB:
- 大部分 LMDB 可常驻内存，基本消除抖动
- 预计速度提升 +40-60%
```

#### 成本
- 额外 16GB DDR4 内存: ¥150-200（一次性）
- 安装: 15 分钟

#### 收益
- **升级到 32GB**: +15-25%（从 2.09 → 2.4-2.6 it/s），mmap 抖动减轻但未消除
- **升级到 64GB**: +40-60%（从 2.09 → 3.0-3.3 it/s），大部分 LMDB 可常驻内存
- **长期价值**: 未来的所有训练任务都受益

#### 建议
问导师："能否为 jqlab4090 服务器再加一条 16GB 内存条？"

---

### 方案 I: HDF5 格式（不推荐）

#### 提议理由
HDF5 是科学计算标准格式，可能避免 mmap 问题

#### 实际情况
HDF5 通过 h5py 支持按需读取单条记录（`dataset[idx]`），**不需要**加载整个文件到内存。
这一点与 LMDB 的 mmap 不同——LMDB 会把整个文件映射到虚拟地址空间。

但在我们的场景下仍不推荐，原因是：
1. **迁移成本高**：需要重写全部数据加载代码，预计 3-5 天
2. **随机小块读取性能不如 LMDB**：LMDB 的 B+ 树索引在随机 key-value 查询上更快
3. **多 worker 并发读取需额外配置**：HDF5 需要 `swmr=True`（Single Writer Multiple Reader），增加复杂度
4. **现有 LMDB 配合 `readahead=False` 已能有效缓解问题**

#### 结论
**不推荐** — 不是因为 HDF5 有技术缺陷，而是迁移的时间成本与收益不匹配。

# 需要安装: pip install torch_cluster
import torch_cluster

def get_edge_index_gpu(coords):
    """使用 PyTorch 在 GPU 上计算 k-NN"""
    if not isinstance(coords, torch.Tensor):
        coords = torch.from_numpy(coords).float()

    # 如果需要在 GPU 上运行
    coords_gpu = coords.cuda() if torch.cuda.is_available() else coords

    # torch_cluster.knn_graph 返回边索引
    # edge_index: (2, num_edges) 张量
    edge_index = torch_cluster.knn_graph(coords_gpu, k=32, flow='target_to_source')

    return edge_index.cpu() if torch.cuda.is_available() else edge_index

## 附录 E：学术界与工业界权威方案调研（2026-03-15 补充）

### E.1 三大主流方向

经过网络搜索和文献调研，学术界和工业界针对 GNN 数据加载瓶颈，目前有三个主流方向：

#### 方向一：离线预处理 + 分片存储（最主流）

**PyTorch 官方推荐 WebDataset 格式**。核心思路：把数据打包成 tar 分片（每个几百 MB 到几 GB），训练时顺序读取。

- PyTorch 官方博客专门发文推荐，称比随机读取快 **3-10 倍**
- 已有 50TB 级数据训练的成功案例
- 与标准 DataLoader 完全兼容
- 支持云存储和对象存储

**对我们的适用性**：中。思路可借鉴，但有两个实际障碍：
1. WebDataset 的核心设计是**顺序读取**，用 shuffle buffer 近似随机化，不是真随机。我们的训练需要 `shuffle=True` 做真随机采样（酶-底物对分布不均匀，真随机对收敛重要）。
2. 我们的数据来自多个 LMDB（enzyme、reaction、grover、structure），一个样本需要从多个数据库取数据再组装。WebDataset 要求每个样本是自包含的 tar 条目，需要预先把多源数据 join 成单样本再打包，数据准备流程要大改。

**参考**：
- PyTorch 官方博客: https://pytorch.org/blog/efficient-pytorch-io-library-for-large-datasets-many-files-many-gpus/
- WebDataset GitHub: https://github.com/webdataset/webdataset
- 50TB 实战案例: https://medium.com/red-buffer/why-did-i-choose-webdataset-for-training-on-50tb-of-data-98a563a916bf

#### 方向二：CPU-GPU 异步流水线化（学术前沿）

多篇顶会论文（NSDI'23、PPoPP'26、HPCA'25）提出的方案。核心思路：把采样/图构建（CPU）和神经网络训练（GPU）拆成独立阶段，用生产者-消费者模式异步并行。

关键发现：
- 典型 DGL 训练中 GPU 利用率仅 **~10%**（BGL, NSDI'23）
- PCIe 数据传输占总执行时间的 **39%**（PiPAD）
- HiFuse 通过将图构建从 GPU 卸载到 CPU + 多线程异步流水线，实现 **2.38 倍加速**

**对我们的适用性**：思路可直接借鉴（即方案 D 的 GPU k-NN 流水线——workers 在 CPU 读数据，主进程在 GPU 算 k-NN）。但这些论文的实现针对百万节点大图，我们的分子图只有几千节点，规模不同。

**代表论文**：
- BGL (NSDI'23): https://www.usenix.org/conference/nsdi23/presentation/liu-tianfeng
- HiFuse (2024): https://arxiv.org/abs/2408.08490
- PiPAD: https://arxiv.org/pdf/2301.00391
- MaxK-GNN: https://arxiv.org/html/2312.08656v5

#### 方向三：LMDB 配置优化（最简单）

多个 PyTorch LMDB 开源项目的社区共识标准配置：

```python
env = lmdb.open(
    path,
    readonly=True,
    readahead=False,   # 关闭预读，随机访问时减少无用页面加载
    meminit=False,     # 跳过内存初始化，减少不必要的页面分配
    lock=False,        # 多 worker 场景避免锁竞争
    max_readers=128    # 匹配 worker 数量
)
```

LMDB 官方文档明确指出：当数据库大于 RAM 且为随机访问模式时，应禁用 readahead。

**对我们的适用性**：直接适用。一行代码改动，零风险。

**参考**：
- LMDB 官方文档: https://lmdb.readthedocs.io/
- PyTorch-LMDB 最佳实践: https://github.com/rmccorm4/PyTorch-LMDB

### E.2 HDF5 评估结论（不推荐，但理由已修正）

之前有建议用 HDF5 替代 LMDB。

**原始否定理由（已修正）**：我们最初引用 SURF 文档称"HDF5 需要把整个文件加载到内存"，这个表述不准确。h5py 支持按需读取（`dataset[idx]` 只读对应磁盘块），不需要加载整个文件。

**正确的不推荐理由**：
1. 迁移成本高：需重写全部数据加载代码，预计 3-5 天
2. HDF5 随机小块读取性能不如 LMDB 的 B+ 树索引
3. 多 worker 并发读取需额外配置（`swmr=True`），增加复杂度
4. 现有 LMDB 配合 `readahead=False` 已能有效缓解问题

**结论不变**：不推荐——不是因为 HDF5 有技术缺陷，而是迁移的时间成本与收益不匹配。

**参考**: https://servicedesk.surf.nl/wiki/display/WIKI/Best+Practice+for+Data+Formats+in+Deep+Learning

## 附录 F：PyG 标准范式 vs 我们的实现（2026-03-15 补充）

### F.1 PyG 的标准数据处理范式

PyTorch Geometric 的 `InMemoryDataset` 和 `Dataset` 基类从一开始就按**离线预处理**设计，分两个阶段：

**阶段 1：预处理（`process()` 方法，只跑一次）**

把原始数据（PDB 文件、SMILES 等）转换成 PyG 的 `Data` 对象（包含 `x`、`edge_index`、`edge_attr` 等），用 `torch.save()` 存成 `.pt` 文件。这一步可能跑几小时，但只做一次。

**阶段 2：训练（反复跑）**

`torch.load()` 读 `.pt` 文件，拿到现成的图对象，不做任何解析坐标或构建 k-NN 边的计算。

```python
# === 在线构建（EZSpecificity 当前做法）===
# 每个 epoch、每个 batch 都重新算 k-NN
def __getitem__(self, idx):
    coords = read_pdb(...)          # 读文件
    edge_index = knn_graph(coords)  # CPU 算 k-NN（慢！占 50-70% 时间）
    data = Data(x=..., edge_index=edge_index)
    return data

# === 离线预处理（PyG 标准做法）===
# process() 里提前算好，存成 .pt
def process(self):
    for idx in range(len(raw_data)):
        coords = read_pdb(...)
        edge_index = knn_graph(coords)
        data = Data(x=..., edge_index=edge_index)
        torch.save(data, f'processed/data_{idx}.pt')

# 训练时直接读，零计算
def __getitem__(self, idx):
    return torch.load(f'processed/data_{idx}.pt')
```

CV 和 NLP 不太遇到这个问题——图像 resize/flip、文本 tokenize 很轻，在线算无所谓。但 GNN 的图构建开销大，所以 PyG 社区从一开始就把离线预处理作为默认范式。

### F.2 我们做对了什么、做错了什么

| | PyG 标准做法 | 我们的 240GB 结构缓存 | 对比 |
|---|---|---|---|
| 是否离线预处理 | ✅ `process()` 里算好 k-NN | ✅ `build_structure_cache.py` 算好 k-NN | **一样** |
| 存储格式 | 每个样本一个 `.pt` 文件 | 全部存进 LMDB 数据库 | **这里不同** |
| 读取方式 | `torch.load()` 读单个文件 | LMDB mmap 映射整个数据库 | **导致了问题** |
| 内存行为 | 只有当前样本在内存（几百 KB） | 整个 240GB 被映射到虚拟内存 | **根本原因** |

**结论**：我们的离线预处理思路完全正确，和 PyG 标准范式一致。问题出在存储格式选择上——用了 LMDB 而不是 `.pt` 文件，导致 mmap 抖动。

### F.3 如果重做，最优方案

如果要在本地 32GB 机器上达到最优性能，应该：

1. 保留现有的预计算逻辑（`build_structure_cache.py`）
2. 把输出格式从 LMDB 改成分目录 `.pt` 文件：
   ```
   structure_cache/
   ├── 000/
   │   ├── sample_0.pt    (~1MB，包含完整的 k-NN 图 + 原子特征)
   │   ├── sample_1.pt
   │   └── ...（每目录 1000 个文件）
   ├── 001/
   │   └── ...
   └── 176/
       └── sample_176842.pt
   ```
3. 训练时 `torch.load()` 读单个文件，内存占用 = 当前 batch 的几个样本

**预估效果**：
- 内存：几十 MB（vs 当前 300GB mmap）→ 彻底消除换页抖动
- 速度：跳过 k-NN 计算 + 无 mmap → 预估 6-10 it/s
- 硬盘：~250GB（与当前 LMDB 缓存相当）
- 缺点：176K 个文件需分目录存储，Windows NTFS 需注意杀毒软件排除

### F.4 为什么现阶段不做这个改造

1. **时间**：毕业论文截止约 1 个月，改造数据管线 + 验证正确性需要 2-3 天
2. **风险**：新管线可能引入 bug，影响训练结果的可复现性
3. **替代方案更快**：租 100GB RAM 服务器（¥0.99/h），LMDB 全进内存，同样效果，无代码改动

**但如果未来继续做 P450 研究（Path C/D），强烈建议迁移到 `.pt` 文件范式。**

### 修正详情

#### G.1 GPU k-NN batch 参数（问题 1）

**原始代码**（错误）：
```python
edges = torch_cluster.knn_graph(coords.cuda(), k=32)  # 缺少 batch 参数
```

**问题**：一个 batch 里多个分子的原子被拼在一起做 k-NN，边缘原子可能连到其他分子的原子上。这是**训练结果出错的 bug**，不是性能问题。

**修正后**：
```python
batch_vec = torch.cat([torch.full((len(c),), i, dtype=torch.long) for i, c in enumerate(coords_list)])
edges = torch_cluster.knn_graph(coords_all.cuda(), k=32, batch=batch_vec.cuda())
```

#### G.2 32GB RAM 收益（问题 2）

**修正后**：升级到 32GB → "mmap 抖动减轻但未消除"（32GB < 60GB），速度 +15-25%。升级到 64GB 才能 +40-60%。
