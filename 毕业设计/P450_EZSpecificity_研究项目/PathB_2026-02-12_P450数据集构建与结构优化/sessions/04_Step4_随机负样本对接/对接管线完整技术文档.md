## 一、为什么要做对接？——背景与动机

### 1.1 EZSpecificity 模型需要什么输入？

EZSpecificity 是一个预测"酶能不能催化某个底物"的 AI 模型。它需要三类输入：

1. **酶的序列信息**（一维）：蛋白质的氨基酸序列 → ESM 嵌入
2. **底物的化学信息**（一维）：分子的 SMILES 式 → Morgan 指纹 + GROVER 嵌入
3. **酶-底物复合物的 3D 结构**（三维）：底物"放进"酶口袋后的 3D 空间构型 → GNN 结构特征

前两类信息我们已经有了（酶序列来自 PDB，SMILES 来自 BRENDA 数据库）。**第三类——3D 结构——才是对接要解决的问题。**

### 1.2 为什么不能直接用实验结构？

对于**正样本**（酶真的能催化这个底物），有些 PDB 结构中确实包含底物，可以直接用。但对于**负样本**（酶不催化这个底物），这个底物根本就没有和这个酶共结晶过——实验室不会去解析一个"不起作用"的复合物结构。

所以，负样本的 3D 结构必须通过**计算模拟**来生成，这就是分子对接的用途。

### 1.3 对接在整个研究中的位置

```
Path A（已完成）：用 PDB 晶体结构中的实验数据做测试
  → 正样本：PDB 中真实的酶-底物复合物
  → 负样本：PDB 中酶-抑制剂复合物（它们会结合但不催化）
  → 结果：AUC-ROC = 0.6636

Path B（当前）：用 AutoDock Vina 对接来生成随机负样本
  → 正样本：把已知底物对接到对应的酶中
  → 负样本：把随机选的底物对接到"不是它的酶"中
  → 目的：模拟论文训练数据的负样本策略（随机配对）
```

我们用 Vina 对接来生成 Path B 所有样本（正样本和负样本）的 3D 结构。

## 二、什么是分子对接？——关键概念

### 2.1 分子对接的本质

分子对接就是用计算机模拟"一个小分子如何放进一个蛋白质口袋"。

想象一下：你手里有一把形状复杂的钥匙（底物），面前有一把锁（酶的活性位点）。你需要找到钥匙插进锁孔的最佳角度和深度——这就是对接在做的事。

更精确地说，对接要回答两个问题：
1. **姿态（Pose）**：底物在口袋中的空间朝向和位置是什么？
2. **亲和力（Affinity）**：这个姿态下，酶和底物之间的结合强度有多大？（单位：kcal/mol，越负越强）

### 2.2 AutoDock Vina

AutoDock Vina 是一个广泛使用的开源对接软件（2010 年发表，截至 2025 年被引用超过 30,000 次）。它的工作原理：

1. **定义搜索空间**：你指定一个长方体盒子（center + size），Vina 只在这个盒子里搜索
2. **生成构象**：Vina 旋转底物的可旋转键，生成不同的 3D 形状
3. **打分**：对每种放置方式，用经验打分函数评估结合强度
4. **优化**：用梯度下降找到打分最优的姿态
5. **输出**：按结合能排序的前 N 个姿态

**Vina vs AutoDock 4**（这一点很重要）：

| 特性 | AutoDock 4（论文用的） | AutoDock Vina（我们用的） |
|------|----------------------|-------------------------|
| 发布年份 | 1998 / 2009 | 2010 |
| 搜索算法 | 拉马克遗传算法 (LGA)：模拟生物进化来搜索最佳构象 | 梯度优化 + 迭代局部搜索：数学优化方法 |
| 打分函数 | 基于原子类型的力场能量图（预计算） | 经验打分函数（实时计算） |
| 电荷处理 | **使用**用户指定的原子电荷 | **忽略**用户电荷（对含金属蛋白可能不利） |
| 速度 | 较慢 | 快约 2 个数量级 |

它们是两个**完全不同的程序**，共享 AutoDock 的名字但算法不同。

### 2.3 输入/输出格式

| 格式 | 全称 | 是什么 | 包含什么 |
|------|------|--------|---------|
| **PDB** | Protein Data Bank | 实验解析的蛋白质 3D 结构 | 原子坐标、残基名、元素类型 |
| **PDBQT** | PDB + Charge + Type | AutoDock 专用格式 | PDB 基础上多了每个原子的电荷(Q)和原子类型(T)，但**没有键序** |
| **SDF** | Structure Data File | 标准化学分子文件 | 原子坐标 + 键序（单键/双键/三键）+ 键类型 |
| **SMILES** | — | 分子的一维文本表示 | 只有化学式，没有 3D 坐标。如 `CCO` = 乙醇 |

**关键理解**：PDBQT 不记录化学键的类型（不知道两个原子之间是单键还是双键），这是对接后"恢复"步骤需要解决的核心问题。

### 2.4 P450 酶的特殊性

P450 是一类含有血红素（Heme）辅因子的酶。血红素的中心是一个铁原子（FE），**所有催化反应都发生在 FE 正上方**。这给了我们一个巨大的便利：不需要复杂的口袋搜索算法——FE 的坐标就是对接盒子的中心。

```
           ┌─────────────────┐
           │   蛋白质外壳     │
           │                 │
           │  ┌──────────┐   │
           │  │ 活性位点  │   │  ← 对接盒子（22.5Å³）
           │  │          │   │
           │  │  [底物]   │   │  ← 底物在这里被对接
           │  │    ↕      │   │
           │  │   ─FE─    │   │  ← 铁原子，盒子中心
           │  │  /HEM\    │   │  ← 血红素辅因子
           │  └──────────┘   │
           │                 │
           └─────────────────┘
```

#### 为什么不能直接用原始 PDB？

原始 PDB 文件是从 RCSB 下载的"原始"数据，里面除了蛋白质，还包含很多对接不需要的东西：

```
原始 PDB 文件内容：
├── 蛋白质原子（我们需要的）
├── HEM 血红素（对接时需要，提取口袋时不需要）
├── 水分子 HOH（不需要——会干扰对接）
├── 离子 Na⁺, Cl⁻（不需要）
├── 缓冲盐（不需要——实验残留物）
├── 共结晶配体（不需要——我们要对接自己的底物）
└── 替代构象 altloc A/B（只需要主构象 A）
```

而且 Vina 不能直接读 PDB 格式——它需要 PDBQT 格式（在 PDB 基础上多了电荷和原子类型信息）。

#### 处理步骤（详细版）

**第 1 步：BioPython 解析与清理**

用 BioPython 的 PDBParser 读取 PDB 文件，然后通过一个自定义的过滤器（`_CleanupSelect`）决定保留哪些原子：

| 原子/残基类型 | 是否保留 | 原因 |
|--------------|---------|------|
| 标准氨基酸（20 种） | **保留** | 蛋白质主体 |
| HEM/HEC/HEA 等血红素残基 | **保留** | 定义活性位点的几何形状；FE 是对接盒子的中心 |
| 水分子 (HOH/WAT) | **删除** | 实验残留，干扰对接 |
| 离子 (Na/K/Cl/Ca/Mg/Zn) | **删除** | 不参与催化反应 |
| 共结晶配体 | **删除** | 我们要对接自己的底物，不能有"已经在口袋里"的配体 |
| 缓冲盐等其他 HETATM | **删除** | 实验试剂残留 |
| 替代构象 B/C | **删除** | 只保留主构象 A |

**第 2 步：清除 altloc 标记**

这是我们在开发过程中遇到的一个 Bug 的修复。

**问题**：有些 PDB 文件中，同一个原子有两套坐标（称为 altloc A 和 altloc B，代表该原子在晶体中有两种可能的位置）。PDB 文件的第 17 列用一个字母标记（A 或 B）。虽然第 1 步已经过滤掉了 B 构象，但如果 A 构象的 altloc 标记没有清除，MGLTools 在给蛋白质加氢原子时，会把 altloc 字母拼进氢原子的名字里——比如生成 `HD2B1` 这样 5 个字符的原子名。PDB 格式规定原子名只能占 4 个字符的列宽，5 个字符会导致后面的所有列（坐标、电荷等）全部错位，Vina 就无法解析了。

**修复**：在送入 MGLTools 之前，把 PDB 文件第 17 列统一替换为空格。

**第 3 步：MGLTools 转换 PDB → PDBQT**

```bash
D:\autodock\MGLTools-1.5.7\python.exe  prepare_receptor4.py \
  -r input.pdb \
  -o output.pdbqt \
  -A hydrogens \         # 添加极性氢原子（对接打分需要）
  -U nphs_lps_waters     # 合并非极性氢、删除孤对电子和水
```

**注意**：参数不能用 `-U nonstdres`（删除非标准残基）——否则会把 HEM 也删掉。

**第 4 步：验证 FE 原子**

转换完成后，检查输出的 PDBQT 中是否包含 FE 原子。如果 MGLTools 意外删除了 FE，这个受体就不能用了（后面没法定位活性位点）。

**第 5 步：中文路径处理**

因为我们的项目路径包含中文（`毕业设计/P450_EZSpecificity_研究项目/...`），而 MGLTools（Python 2.7 程序）不支持中文路径，所以所有 MGLTools 操作都在一个纯英文的临时目录 `D:\autodock\tmp\` 中进行，处理完再复制回来。

**输出**：3D PDBQT 文件 + 参考 SDF 文件

```
                │
                ▼
         配体.pdbqt (434/436 成功)
```

#### 为什么需要这一步？

SMILES 只是一个文本字符串，没有 3D 坐标。比如 `CCO` 代表乙醇（CH₃CH₂OH），但它不告诉你这些原子在空间中的位置。对接需要一个真实的 3D 分子——每个原子都有 (x, y, z) 坐标。

#### 处理步骤

**第 1 步：SMILES → RDKit 分子对象**

RDKit 解析 SMILES 字符串，建立分子的"拓扑"——知道有哪些原子、它们之间怎么连接（单键/双键/芳香键），但还没有 3D 坐标。

**第 2 步：添加氢原子**

SMILES 通常省略氢原子（`CCO` 实际上是 `CH₃-CH₂-OH`，有 9 个原子不是 3 个）。对接需要完整的分子，所以要把省略的氢原子加回来。

**第 3 步：生成 3D 构象**

这是关键步骤。RDKit 的 ETKDGv3 算法利用 Cambridge 结晶数据库中数十万个已知分子的扭转角统计数据，给分子分配合理的 3D 坐标。如果 ETKDGv3 失败，回退到 ETKDG（上一代算法），再失败就用随机坐标。

**第 4 步：能量最小化**

生成的初始 3D 构象可能有一些原子位置不太合理（比如两个原子距离太近）。能量最小化通过 MMFF94 力场（一套描述原子间相互作用的数学模型）微调每个原子的位置，找到能量最低（最稳定）的构象。

**第 5 步：转成 PDBQT**

用 Meeko 库把 RDKit 分子对象转成 Vina 需要的 PDBQT 格式。Meeko 会自动计算每个原子的 Gasteiger 电荷和 AutoDock 原子类型。

同时保存一份 SDF 文件作为参考（SDF 包含完整的键序信息，PDBQT 没有）。

模型训练和评估都需要正负样本：
- **正样本**（Label=1）：酶 A 真的能催化底物 X（来自 BRENDA 文献记录）
- **负样本**（Label=0）：酶 B 不催化底物 X（通过随机配对构造）

### 6.2 采样策略

我们采用**单向随机采样**（与论文训练集 ESIBank 的策略一致）：

**固定底物，随机选"假酶"**。

具体来说，对于每个出现在正样本中的底物 X：
1. 找出 X 的"真实酶"集合——正样本中与 X 配对的酶
2. 候选酶池 = 所有可对接的酶（282 个）**减去** X 的真实酶

**为什么要排除真实酶？** 因为一个底物可能被多个酶催化。如果不排除，可能把"酶 A 催化底物 X"这种实际上是正样本的对采为负样本。

为什么从 1000 开始？B6 数据集的原始 Dock_Index 范围是 0-515，从 1000 开始可以完全避免编号冲突。

### 7.1 单次对接的过程

对于 manifest 中的每一对（比如 dock_index=1000，酶 5NCB + 底物 23）：

1. **查找输入文件**：
   - 受体 PDBQT：`receptors/pdbqt/5NCB.pdbqt`
   - 配体 PDBQT：`ligands/pdbqt/substrate_23.pdbqt`
   - 盒子参数：`receptors/grid_boxes/5NCB_grid.json`
   - 原始 PDB：`PathA/.../01_Step1_PDB文件/5NCB.pdb`（后处理需要）

2. **调用 Vina**：
   ```bash
   D:\autodock\vina.exe \
     --receptor 5NCB.pdbqt \
     --ligand substrate_23.pdbqt \
     --center_x 10.234 --center_y 20.456 --center_z 30.678 \
     --size_x 22.5 --size_y 22.5 --size_z 22.5 \
     --exhaustiveness 8 \
     --num_modes 9 \
     --energy_range 3 \
     --cpu 1 \
     --out docked_1000.pdbqt
   ```

3. **Vina 的工作过程**（用户看不到，在内部执行）：
   - 把配体放进蛋白质口袋
   - 旋转配体的可旋转键，改变配体的形状
   - 在盒子范围内尝试不同的位置和朝向

   - 用梯度下降优化最佳姿态
   - 输出最多 9 个最佳构象，按结合能排序

4. **输出**：
   - `docked_1000.pdbqt`——包含对接后配体的 3D 坐标
   - 结合能（从 stdout 解析），如 `-6.4 kcal/mol`

### 7.2 对接参数详解

| 参数 | 值 | 含义 |
|------|-----|------|
| `exhaustiveness` | 8 | 搜索彻底度。Vina 会用 8 个独立的随机起点来搜索最佳构象，然后取最好的结果。值越大越准但越慢。 |
| `num_modes` | 9 | 最多输出 9 个不同的对接构象。我们只取第 1 个（结合能最好的）。 |
| `energy_range` | 3 | 只输出与最佳构象的结合能差距在 3 kcal/mol 以内的构象。 |
| `cpu` | 1 | Vina 内部只用 1 个 CPU 核心。并行在 Python 层用 ProcessPoolExecutor 实现。 |
| 超时 | 300s（首轮）/ 600s（重试） | 超过这个时间还没完成就标记为失败。 |

### 7.3 并行策略

2,797 对如果串行跑，按平均 75 秒/对计算需要 58 小时。我们用 Python 的 ProcessPoolExecutor 同时跑 **12 个对接任务**，总时间约 4.9 小时。

为什么是 12 个而不是更多？
- 电脑有 12 个 CPU 核心
- 每个 Vina 进程用 1 核
- 留一点 CPU 余量给操作系统和日志写入

### 7.4 断点续跑机制

全量对接需要几个小时，如果中途断电或出错不能从头重来。所以设计了**双 CSV 架构**：

- **manifest.csv**（不可变）：定义了 2,797 对任务，创建后永远不修改
- **progress.csv**（持续更新）：记录每对的状态（success/failed/pending），每完成 50 对就更新一次

如果中断后重启，脚本读取 progress.csv，找到还没完成的任务继续跑。

progress.csv 使用**原子写入**（先写到临时文件，再原子重命名）防止写入过程中中断导致文件损坏。

### 8.1 从 PDBQT 恢复配体

**问题**：PDBQT 格式不记录化学键类型。比如苯环上的碳碳键是芳香键，但 PDBQT 中只有原子坐标和类型，看不出来。下游的 GNN 模型需要完整的化学信息（原子类型 + 键类型），所以必须"恢复"键序。

**解决方案**：用 Meeko 库。Meeko 在最初把 RDKit 分子转成 PDBQT 时，会在 PDBQT 文件的注释行中嵌入一些映射信息。对接后，Meeko 读回 PDBQT，利用这些映射信息恢复原始的键序和原子类型。

```python
from meeko import PDBQTMolecule, RDKitMolCreate

# 读取 Vina 对接后的 PDBQT
pdbqt_mol = PDBQTMolecule.from_file("docked_1000.pdbqt")

# 恢复为完整的 RDKit 分子（包含 3D 坐标 + 键序）
poses = RDKitMolCreate.from_pdbqt_mol(pdbqt_mol)
best_pose = poses[0]  # 取结合能最好的第 1 个构象
```

恢复后保存为 SDF 文件 → `raw_ligand/{dock_index}.sdf`

### 8.2 质量检查

每个对接结果都经过两项质量检查：

**检查 1：重原子数一致性**

从 SMILES 算出底物应该有多少个重原子（非氢原子），与 Meeko 恢复的分子对比。如果不一致，说明 Meeko 恢复过程中丢失或多出了原子——这个结果不能用。

**检查 2：FE-配体距离**

计算对接后配体的每个原子到 HEM 铁原子（FE）的距离，取最小值：

| 距离范围 | 含义 | 处理 |
|---------|------|------|
| < 1.5Å | 原子物理重叠（不可能发生） | **拒绝** |
| 1.5-15Å | 配体在活性位点附近（正常） | **通过** |
| > 15Å | 配体飞出了活性位点 | **拒绝** |

为什么是 1.5Å 而不是 0？因为 Fe 原子的范德华半径约 2.0Å，配体原子的范德华半径约 1.5-2.0Å。两个原子中心距离 < 1.5Å 意味着它们在物理上穿透了彼此——这是对接软件的计算错误，不是真实的结合姿态。

（注：最初阈值设为 2.0Å，在重试阶段降为 1.5Å。详见第十节。）

### 8.3 口袋提取

**什么是口袋**：不是整个蛋白质——蛋白质可能有几千个原子，但大部分离配体很远，对结合没有影响。口袋是**配体附近的蛋白质片段**，只包含直接参与结合的残基。

**提取方法**：
1. 收集原始 PDB 中所有蛋白质重原子（标准 20 种氨基酸，排除水/离子/HEM/氢原子）
2. 用 BioPython 的 NeighborSearch 构建空间索引（KD-tree）
3. 对对接配体的每个原子坐标，查询 10Å 半径内的蛋白质原子
4. 取所有查询结果的并集 → 这就是口袋

**为什么排除 HEM？** Gate A 实验（Step 2 因子实验）已经证实：加入 HEM 会严重损害模型性能（AUC-ROC 从 0.71 降到 0.49）。原因是 HEM 中的 Fe 原子不在 EZSpecificity 模型的原子词汇表中，模型不认识它，会产生 OOD（Out-Of-Distribution）噪声。

**为什么是 10Å？** 同样是 Gate A 实验确定的最佳值。10Å 覆盖了主要的氢键和范德华作用力范围，更大的半径（15/20Å）只增加了远处不相关的残基，效果提升不明显。

**输出**：`pocket/{dock_index}.pdb`——只包含口袋原子的标准 PDB 格式文件。

### 8.4 后处理总结

对于一个成功的对接（比如 dock_index=1000）：

```
输入:
  docked_1000.pdbqt (Vina 输出)
  5NCB.pdb (原始 PDB)

处理:
  1. Meeko 恢复配体 → RDKit 分子 (含 3D 坐标 + 键序)
  2. QC: 重原子数 ✓, FE 距离 3.26Å ✓
  3. NeighborSearch 提取 10Å 口袋 (364 个蛋白质原子)

输出:
  data/04_Step4_批量对接/pocket/1000.pdb     (口袋, 364 个原子)
  data/04_Step4_批量对接/raw_ligand/1000.sdf  (配体, 含 3D 坐标和键序)
```

这两个文件的格式与下游管线（Step 5-10）完全兼容，不需要任何额外的格式转换。

## 十、重试策略与结果（Step 4b）

**脚本**：`step4b_retry_failed.py`

首次运行有 267 对失败。我们用三层渐进式重试策略恢复了其中 236 对。

### 10.1 三层重试策略

#### Tier 0：FE 距离阈值放宽（15 对 → 15 对恢复）

**问题**：首次运行用 FE_DISTANCE_MIN=2.0Å 作为质量阈值。但这 15 对的距离都在 1.5-2.0Å 之间，属于"物理上可接受但接近原子半径之和"的边界区域。

**修改**：将 FE_DISTANCE_MIN 从 2.0Å 降到 1.5Å。

**为什么这样做是安全的**：
- 对接精度本身有 1-2Å 误差
- 口袋配置是 noHeme（模型看不到 FE），FE 距离只是定位参考
- 1.5Å 仍然安全地过滤掉了真正的原子重叠（< 1.5Å）
- 这 15 对都是负样本（随机配对），物理精度不是关键

**操作**：不需要重新对接——只重新跑 postprocess（从已有的 `docked.pdbqt` 重新提取口袋和配体，用新阈值）。

**结果**：**15/15 = 100% 恢复**。

#### Tier 1：延长超时（252 对 → 122 对恢复）

**问题**：252 对因 Vina 在 300 秒内没完成而超时。

**修改**：超时从 300s 提高到 600s，exhaustiveness 保持 8。

**结果**：**122/252 = 48.4% 恢复**。

分析：大约一半的超时对接在 300-600s 之间就能完成——它们的底物不算特别大，只是比 300s 稍微多需要一点时间。剩下的一半即使 600s 也不够。

#### Tier 2：降低搜索强度（130 对 → 99 对恢复）

**问题**：Tier 1 后还有 130 对超时。

**修改**：exhaustiveness 从 8 降到 4（搜索空间减半），超时保持 600s。

**为什么降低搜索强度？** exhaustiveness=4 意味着 Vina 用更少的随机起点搜索，找到的构象可能不是全局最优，但对于负样本（随机配对）来说完全够用——我们不需要精确的结合姿态，只需要一个"大致合理"的 3D 构型。

**结果**：**99/130 = 76.2% 恢复**。恢复率反而比 Tier 1 更高，因为搜索空间减半使得原本来不及的大分子现在能在 600s 内完成。

### 10.2 不可恢复的 31 对

| 失败类型 | 数量 | 具体情况 |
|---------|------|---------|
| Vina 超时 | 30 | 涉及 3 个极大底物（substrate_246/247/248），23-26 个可旋转键，是 CoA-脂肪酸硫酯类长链分子 |
| FE 距离 1.08Å | 1 | dock_1417 (PDB 6WGW)，真正的原子重叠，不可接受 |

这 31 对占总数的 1.1%，对数据集质量无实质影响。

## 十二、对接管线 vs 论文原始方法——关键差异

### 12.1 论文是怎么做的？

**关键发现**：论文的开源代码中**不包含对接脚本**。代码只包含推理管线（从已有的 PDB 文件到预测结果），不包含"怎么生成这些 PDB 文件"。

根据论文描述和 CLAUDE.md 中的信息，论文训练集 ESIBank 的结构数据：
- **蛋白质结构**：AlphaFold 预测结构（不是实验结构）
- **对接工具**：AutoDock（不是 Vina）
- **负样本**：随机配对
- **规模**：约 65,000 对（323,783 总对的一个子集）
- **评估场景**："Unknown enzyme + Unknown substrate" AUC-ROC = 0.7198

### 12.2 差异对比

| 方面 | 论文 (ESIBank) | 我们 (Path B Step 4) |
|------|---------------|---------------------|
| **对接工具** | AutoDock 4 (LGA 遗传算法) | AutoDock Vina 1.2.7 (梯度优化) |
| **打分函数** | 力场能量图（预计算） | 经验打分函数（实时） |
| **电荷处理** | 使用用户电荷 | **忽略**用户电荷 |
| **蛋白质结构** | AlphaFold 预测 | PDB 晶体实验结构 |
| **酶种类** | 8,124 种（ESIBank 全库） | 152 种 P450（0% 与训练集重叠） |
| **负样本策略** | 随机配对 | 随机配对（一致） |
| **正负比** | 1:9.36 | 1:9.44（接近） |
| **数据规模** | ~65,000 对 | 2,766 对 |
| **口袋半径** | 10Å | 10Å（一致） |

### 12.3 哪些差异可能影响结果？

**影响大的**：
1. **对接工具不同**：AD4 和 Vina 的打分函数和搜索算法完全不同，生成的对接姿态分布也不同。模型在 AD4 生成的姿态上训练，Vina 生成的姿态属于"分布外"数据。
2. **电荷忽略**：Vina 忽略用户指定的原子电荷。对 P450 这种含铁金属蛋白，FE 的电荷分布对配体结合有影响，Vina 无法正确建模。
3. **酶种类 0% 重叠**：模型从未见过任何 P450 酶，不知道 P450 的结合偏好。

**影响中等的**：
4. **AF2 vs 晶体结构**：模型训练用 AlphaFold 结构，我们测试用晶体结构。通常晶体结构更准确，但训练/测试分布不匹配可能带来噪声。

**影响小的**：
5. **格式/键序**：我们的 Meeko + Step 8 对齐 pipeline 正确恢复了键序信息，且 2,766/2,766 = 100% 的 LMDB 生成成功率证实了格式兼容性。

## 十三、对接对 AUC-ROC 的影响分析

### 13.1 Step 5 结果回顾

用 Step 4 的 2,766 个对接复合物跑完推理管线后，得到 **AUC-ROC = 0.5170**——接近随机猜测（0.5）。

对比 EXP01（Path B Step 2，使用 PDB 晶体结构 + 抑制剂负样本）的 AUC-ROC = 0.7115，性能严重下降。

### 13.2 分数分布分析

| 数据集 | 正样本均分 | 负样本均分 | 分离度 |
|--------|-----------|-----------|--------|
| Step 5 (Vina 对接 + 随机负) | -2.94 | -3.20 | **0.26** |
| EXP01 (晶体结构 + 抑制剂负) | -3.00 | -5.51 | **2.51** |

正样本分数几乎一样（~-3.0），但负样本分数完全不同：
- EXP01 的负样本（抑制剂，晶体结构）得分很低（-5.51），模型能轻松区分
- Step 5 的负样本（随机配对，Vina 对接）得分接近正样本（-3.20），模型无法区分

### 13.3 对接是主因吗？

**Codex 分析结论（根因排序）**：

| 排名 | 原因 | 严重程度 | 是否对接问题？ |
|------|------|---------|--------------|
| **1** | 可对接 ≠ 可催化：Vina 让随机分子也能产生"看起来合理"的对接姿态 | **主要** | 是（但本质是对接方法的固有局限，不是 bug） |
| **2** | AD4 → Vina 打分/姿态分布偏移 | 较大 | 是 |
| **3** | 0% 酶重叠（模型从未见过 P450） | 较大 | 否 |
| **4** | AlphaFold → 晶体结构分布偏移 | 中等 | 部分相关 |
| **5** | 格式/键序/管线 bug | 低 | 已排除 |

**核心矛盾**：Vina 的工作是"把分子放到口袋里的最佳位置"——它对任何分子都会尽力找一个最好的位置，无论这个分子是不是真的底物。所以 Vina 生成的对接姿态对正样本和负样本来说**看起来都很合理**，模型在结构层面无法区分它们。

这不是 Vina 的 bug——这是**对接方法的根本局限**。对接模拟的是"几何契合度"和"结合亲和力"，但酶催化的特异性不仅取决于能不能结合，还取决于电子结构、反应路径、过渡态稳定化等更深层的化学因素，这些是对接无法捕捉的。

### 13.4 改进对接能解决问题吗？

**可以部分改善，但无法根本解决**。

可能的改进：
- 使用 `vina --scoring ad4`（Vina 支持 AD4 打分函数模式）
- 缩小对接盒子（22.5Å 可能过大，让随机分子有更多"合理位置"可放）
- 提高 exhaustiveness（提高对接精度）
- 使用 AlphaFold 预测结构替代晶体结构（匹配训练分布）

但即使全部改进，**"可对接 ≠ 可催化"** 和 **"0% 酶重叠"** 这两个根本问题仍然存在。真正的解决方案需要 **Path C（P450 专项微调）**——让模型在 P450 数据上训练，学习 P450 特有的催化识别模式。

## 附录 A：术语表

| 术语 | 含义 |
|------|------|
| **AUC-ROC** | 模型区分正负样本能力的指标，范围 0-1。0.5 = 随机猜测，1.0 = 完美区分。 |
| **altloc** | PDB 文件中同一原子的多套坐标（替代构象）。晶体中某些原子有两种空间位置。 |
| **AutoDock / Vina** | 分子对接软件。AutoDock 4 用遗传算法，Vina 用梯度优化。两个是不同的程序。 |
| **BRENDA** | 酶学数据库，收录了文献中报告的酶催化反应信息。 |
| **ETKDGv3** | RDKit 的 3D 构象生成算法，基于已知分子的扭转角统计数据。 |
| **exhaustiveness** | Vina 的搜索彻底度参数。值越大结果越可靠但越慢。 |
| **GNN** | 图神经网络。EZSpecificity 用 SE(3)-等变 GNN 处理 3D 结构。 |
| **HEM / Heme** | 血红素，P450 酶的核心辅因子。中心有一个铁原子 (FE)，是催化反应的活性位点。 |
| **HETATM** | PDB 中的非标准残基原子（配体、辅因子、水、离子等），区别于标准氨基酸的 ATOM 记录。 |
| **kcal/mol** | 结合能的单位。越负（如 -8.0）表示结合越强。 |
| **KD-tree** | 空间索引数据结构，用于快速查询"某点附近有哪些原子"。 |
| **LMDB** | 高性能键值数据库，用于存储模型特征（比逐个读文件快得多）。 |
| **Meeko** | Python 3 库，处理 PDBQT 格式转换，能恢复 PDBQT 中丢失的键序信息。 |
| **MGLTools** | AutoDock 的辅助工具集（Python 2.7），用于蛋白质 PDB → PDBQT 转换。 |
| **MMFF94** | 分子力场（Merck Molecular Force Field），用于能量最小化。 |
| **OOD** | Out-Of-Distribution，分布外数据。模型没见过的数据类型，预测可能不准。 |
| **PDB** | Protein Data Bank 格式/数据库。记录蛋白质 3D 结构。 |
| **PDBQT** | AutoDock 专用分子格式。PDB + 电荷 (Q) + 原子类型 (T)，但不含键序。 |
| **SDF** | 标准化学分子文件格式，包含完整的 3D 坐标和键序信息。 |
| **SMILES** | 分子的一维文本表示。如 `CCO` = 乙醇, `c1ccccc1` = 苯。 |
| **可旋转键** | 分子中可以自由旋转的化学键。越多 → Vina 搜索空间越大 → 对接越慢。 |
| **范德华半径** | 原子的"有效大小"。两个非键合原子的最短距离约为两者 VdW 半径之和。 |

### C.1 评估方法论

| 维度 | 指标 | 我们能评估吗？ |
|------|------|-------------|
| **Pose quality（姿态质量）** | RMSD vs 实验结构 | 仅正样本（有共结晶结构时） |

| **Screening power（筛选能力）** | 正负样本结合能分离度 | **能**——对比正负样本 |

**不能做的**：Redocking RMSD（需要对晶体结构中的共结晶配体重新对接并比较坐标，属于额外实验）。

### C.7 专业评估方法参考（CADD 领域标准）

以下方法在本次评估中**未执行**，但在专业文献中是标准做法：

| 方法 | 说明 | 我们是否需要？ |
|------|------|-------------|
| **Redocking** | 把晶体配体取出再对接回去，计算 RMSD。< 2Å = 成功 | **推荐做**（对正样本中有共结晶配体的 case） |
| **Cross-docking** | 把 A 蛋白的配体对接到 B 蛋白，检验特异性 | 不需要（我们做的就是这个） |
| **Consensus scoring** | 用多个打分函数（Vina + AD4 + Vinardo）取共识 | 可选（可用 `--scoring ad4`） |
| **Interaction fingerprint** | 分析配体-蛋白质的氢键/疏水相互作用模式 | 可选（需额外工具如 PLIP） |
| **Ligand strain energy** | 对接后配体的内部应变能（构象扭曲程度） | 可选（需 RDKit 力场计算） |
