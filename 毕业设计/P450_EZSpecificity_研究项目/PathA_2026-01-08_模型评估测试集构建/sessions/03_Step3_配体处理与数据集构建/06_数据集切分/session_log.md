### 问题：为什么682会变成436？

让我们**一步一步**追踪数据：

---

### Step 1: 起点 - 682条记录

```
我们有682条记录，每条记录长这样：
┌────────────────────────────────────────┐
│ 记录编号 | PDB  | 配体CCD | 酶UniProt │
├────────────────────────────────────────┤
│ REC_0001 | 1W0F | HEM     | P10635   │
│ REC_0002 | 1W0G | HEM     | P10635   │  ← 注意：HEM又出现了
│ REC_0003 | 3A4U | HEM     | P08684   │  ← HEM再次出现
│ REC_0004 | 3A4U | KTZ     | P08684   │
│ ...      | ...  | ...     | ...      │
│ (共682条)                              │
└────────────────────────────────────────┘
```

**关键发现**：配体CCD会重复！比如HEM（血红素）在682条记录中出现了很多次。

---

### Step 2: 统计唯一配体 - 得到543个

```
我们把682条记录的配体CCD列拿出来，去重：
┌────────────────────────────────────────┐
│ 唯一配体列表（按出现次数排序）          │
├────────────────────────────────────────┤
│ HEM → 出现150次                        │
│ FAD → 出现20次                         │
│ NAP → 出现15次                         │
│ ... → 其他540个配体，各出现1-5次       │
├────────────────────────────────────────┤
│ 总计：543个唯一配体CCD                 │
└────────────────────────────────────────┘

计算验证：
150(HEM) + 20(FAD) + 15(NAP) + ... = 682条记录 ✓
去重后 = 543个唯一CCD ✓
```

**682 → 543的原因**：去重配体CCD，HEM等高频配体被合并了。

---

### Step 3: 配体分类 - 4种类型

现在我们对这682条记录（不是543个配体！）进行分类：

```
┌────────────────────────────────────────┐
│ 分类结果（基于682条记录）               │
├────────────────────────────────────────┤
│ SUBSTRATE (底物)     272条             │
│ PRODUCT (产物)        23条             │
│ INHIBITOR (抑制剂)   244条             │
│ EXCLUDE (排除)       143条             │
├────────────────────────────────────────┤
│ 合计                 682条 ✓           │
└────────────────────────────────────────┘

⚠️ 重要：EXCLUDE的143条不进入模型！
```

---

### Step 4: 排除EXCLUDE类 - 剩539条

```
我们只保留前3类（SUBSTRATE + PRODUCT + INHIBITOR）：

272 + 23 + 244 = 539条记录

这539条记录会进入B3数据集。
```

**682 → 539的原因**：排除了143条EXCLUDE类记录。

---

### Step 5: 提取SMILES - 得到436个

现在处理这539条记录的配体：

```
第1步：从539条记录中提取配体CCD并去重
┌────────────────────────────────────────┐
│ 539条记录 → 提取配体CCD → 去重         │
│                                        │
│ 结果：这539条记录使用了436个唯一CCD    │
│      （539条记录，配体重复出现103次）  │
└────────────────────────────────────────┘

第2步：每个CCD转换为SMILES
┌────────────────────────────────────────┐
│ CCD代码通过RCSB API查询化学结构        │
│ 每个CCD对应一个唯一的SMILES             │
│                                        │
│ 436个唯一CCD → 436个唯一SMILES         │
│ （在539条有效记录范围内，无SMILES碰撞）│
└────────────────────────────────────────┘

为什么539条记录只有436个唯一CCD？
┌────────────────────────────────────────┐
│ 因为同一配体在多条记录中重复出现：      │
│                                        │
│ 例如：                                 │
│ - 配体HEM在10条不同记录中出现          │
│ - 配体KTZ在5条不同记录中出现           │
│ - 配体MEL在3条不同记录中出现           │
│                                        │
│ 539条记录 ÷ 436个唯一CCD = 1.24       │
│ 平均每个CCD出现1.24次                  │
└────────────────────────────────────────┘
```

**539条记录 → 436个SMILES的原因**：
- 去重配体（同一配体在多条记录中出现）
- 539条记录实际只使用了436种不同的配体（CCD代码）

**关于SMILES碰撞的说明**：
```
┌────────────────────────────────────────────────────────────┐
│ Q: 全部543个CCD中有1对碰撞(RFA/RFB)，为什么436个没碰撞？  │
├────────────────────────────────────────────────────────────┤
│ A: RFA和RFB都被分类为EXCLUDE，不在539条有效记录中！       │
│                                                            │
│ 详情：                                                     │
│ - RFA: REC_0186 (pdb_id=1K2O, CYP101A1) → EXCLUDE         │
│ - RFB: REC_0187 (pdb_id=1K2O, CYP101A1) → EXCLUDE         │
│                                                            │
│ 碰撞原因：                                                 │
│ RFA/RFB是钌(Ru)复合物的Delta/Lambda立体异构体，           │
│ 但SMILES格式无法编码金属中心的立体化学信息，              │
│ 导致两者的SMILES字符串完全相同。                          │
│                                                            │
│ 结论：                                                     │
│ 进入模型的436个唯一CCD中，无SMILES碰撞问题。              │
└────────────────────────────────────────────────────────────┘
```

### 总结：数字变化的完整路径

```
682条记录（原始数据）
  ↓
  │ 统计：有543个唯一CCD配体
  │
  ↓ 【排除143条EXCLUDE类】
  │
539条有效记录（进入B3）
  ↓
  │ 这539条记录使用了436个唯一CCD
  │
  ↓ 【CCD转SMILES，无碰撞】
  │
436个唯一SMILES（Substrates.csv）
```

---

### 最简单的理解方式

把682条记录想象成**682张发票**：

1. **682张发票** = 原始数据
2. 发票上的商品有重复（HEM买了150次）→ 实际只有**543种商品**
3. 其中143张发票是"退货单"（EXCLUDE）→ 剩**539张有效发票**
4. 这539张发票购买的商品去重后 → 只有**436种不同商品**

**最终输出**：
- `Enzymes.csv` = 292个供应商（酶）
- `Substrates.csv` = 436种商品（SMILES）
- `B3_完整数据集_272pos267neg/data.csv` = 539张发票（酶-配体对）

## ⚠️ 重要：2026-01-28 BUG修复说明

### 发现的关键BUG

**问题**: build_datasets.py v1版本假设`record_id REC_0001`对应`独立测试集_682条.csv`的第0行。
**验证**: 通过pdb_id匹配测试，匹配率仅**0.1%**（682条中只有1条匹配）。
**根因**: `record_id`是在配体分类并行验证时从`主审核文件_682条P450配体分类.csv`生成的，与`独立测试集_682条.csv`的行顺序完全不同。

| Claude | 验证BUG，实施修复 |

### 修复方案

**正确的数据流**:
```
chunk_*.csv (record_id → pdb_id, ligand_ccd, uniprot_id)
     ↓ JOIN on record_id
merged.csv (record_id → final_class)
     ↓
ccd_smiles.csv (ligand_ccd → SMILES)
     ↓
record_enzyme_mapping.csv ((pdb_id, ligand_ccd) → Enzyme_Index)
     ↓
Output: Substrates.csv, B1-B6各方案data.csv
```
